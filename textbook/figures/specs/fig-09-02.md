# fig-09-02

- **type:** diagram (schematic)
- **purpose:** Show how content provenance (C2PA Content Credentials, specification 2.2) travels with a file from creation to validation, how editing adds signed manifests, what a manifest contains (assertions, hashed claim, claim signature), how a soft binding (watermark or fingerprint) can recover a stripped manifest, and that provenance is not a truth check.
- **caption:** Figure 9.2: A simplified content provenance pipeline (C2PA Content Credentials). A camera or AI tool creates content and signs a manifest whose actions begin with “created”; an editing step adds a new signed manifest (“opened”) that keeps the earlier file and its manifest as an ingredient; a validator checks the signatures, certificates and hashes, including whether the hard binding still matches the file. Inside each manifest, a claim lists every assertion by its hash and is digitally signed and time-stamped. If the manifest is stripped, a soft binding (watermark or fingerprint) can be used to find a copy in a cloud repository. Provenance shows where content came from, not whether it is true. Schematic. Diagram by the author, based on @c2pa2025content and @c2pa2025c2pa.

## content

Top row (boxes, left to right, solid arrows 1 → 2 → 3 → 4):
1. **"Create"** — "Camera or AI tool signs manifest 1; its actions begin with “created”"
2. **"Edit"** — "Editor adds manifest 2 (“opened”); manifest 1 becomes an ingredient"
3. **"Publish"** — "Platform displays Content Credentials"
4. **"Validate"** — "Signatures, certificates and hashes; does the hard binding match?"

Callout above box 4 (rounded, grey): **"Provenance ≠ truth"** / "Records origin, not accuracy".

Under box 1, dotted tag: "Optional invisible watermark in content".

Recovery path (dashed): from the arrow between boxes 2 and 3 down to **"Manifest stripped (e.g. re-encoding)"** → **"Soft-binding lookup in a cloud repository"** → curved dashed arrow up to box 4, labelled "copy of the manifest".

Bottom panel (dashed frame) titled **"Inside each manifest"**, three boxes with solid arrows:
- **"Assertions"**: • Actions: “created” or “opened”, then edits; AI output marked trainedAlgorithmicMedia • Ingredients: earlier files and their manifests • Hard binding: hash of the file’s bytes • Soft binding: watermark or fingerprint
- arrow labelled "hashed" → **"Claim"**: "Lists every assertion by its cryptographic hash"
- arrow labelled "signed" → **"Claim signature"**: "COSE_Sign1, made with the key of an X.509 certificate; RFC 3161 time-stamp"

Technical basis (C2PA Technical Specification 2.2, sections 9.2–9.3, 10, 13–15, 18): a standard manifest contains exactly one hard-binding assertion (c2pa.hash.data / boxes / bmff); the claim references assertions by hashed URIs; all signatures are COSE_Sign1_Tagged with X.509 certificates; RFC 3161 time-stamps are stored in the COSE header; the first actions assertion starts with c2pa.created or c2pa.opened (opened references a parentOf ingredient); soft bindings (watermark or fingerprint) are used to discover a manifest in a manifest repository and "shall not be used as a hard binding". [c2pa2025content; c2pa2025c2pa]

Style: greyscale; solid arrows for the normal path, dashed for the recovery path.
